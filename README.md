# mini-calculator (Mini NPU Simulator)

코디세이 AI 올인원 2기 3주차 과제 'AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기'

입력 패턴이 십자가(Cross) 필터와 X 필터 중 어느 쪽에 더 가까운지를
MAC(Multiply-Accumulate) 연산으로 판별하는 파이썬 콘솔 애플리케이션입니다.

---

## 1. 실행 방법

```bash
python main.py        # (환경에 따라 python3 main.py)
```

- Python 3.8 이상, 외부 라이브러리 없음 (`json`, `time`, `os` 표준 라이브러리만 사용)
- `data.json`은 `main.py`와 **같은 폴더**에 있어야 합니다. (없으면 안내 문구 출력 후 메뉴로 복귀)

```
=== Mini NPU Simulator ===

[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
0. 종료
선택:
```

| 모드 | 동작 |
| --- | --- |
| 1 | 3x3 필터 A, B 입력 → 저장 확인 → 패턴 입력 → MAC 연산 → 판정 → 3x3 성능 분석 |
| 2 | 필터 로드 → 패턴 로드/검증 → MAC/판정/PASS-FAIL → 성능 분석(3x3, 5x5, 13x13, 25x25) → 결과 요약 |

모드 1의 입력은 **한 줄에 3개 숫자를 공백으로 구분**해 3줄씩 입력합니다.
행/열 개수가 맞지 않거나 숫자로 바꿀 수 없는 값이 들어오면 안내 문구를 출력하고
해당 행렬을 처음부터 다시 입력받습니다.

```
필터 A (3줄 입력, 공백 구분)
0 1
입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요. (입력된 개수: 2)
-> 처음부터 다시 입력해 주세요.
```

## 2. 구현 요약

### 데이터 구조 — `Matrix`

n×n 실수 배열을 담는 클래스입니다. `get(row, col)` / `set(row, col, value)`로
특정 위치의 값을 읽고 쓸 수 있고, `Matrix.from_rows()`가 다음을 검증합니다.

- 리스트인지 / 비어 있지 않은지
- 행 수와 열 수가 같은 정사각형인지
- 원소가 숫자인지 (아니면 `ValueError`)

3x3, 5x5, 13x13, 25x25 모두 같은 클래스로 처리하며,
`build_pattern(size, kind)`으로 임의 크기의 십자가 / X 패턴을 만들 수 있습니다.
(`data.json`에 3x3 데이터가 없으므로 성능 분석의 3x3 항목에 사용)

### MAC 연산

```python
for row in range(size):
    for col in range(size):
        total += pattern.get(row, col) * filter_matrix.get(row, col)
```

이중 반복문으로 같은 위치의 값을 곱해 누적합니다. NumPy 등 벡터화 라이브러리는 사용하지 않았습니다.
패턴과 필터의 크기가 다르면 `ValueError`를 던지고, 호출하는 쪽에서 그 케이스만 FAIL 처리합니다.

### 라벨 정규화

`data.json`은 같은 개념을 두 가지 표기로 적고 있습니다.

| 위치 | 표기 | 표준 라벨 |
| --- | --- | --- |
| `patterns[*].expected` | `"+"`, `"x"` | `Cross`, `X` |
| `filters.size_N` 키 | `"cross"`, `"x"` | `Cross`, `X` |

`"+"`와 `"cross"`는 글자만 다를 뿐 같은 대상이므로, 그대로 두면 `expected == verdict` 비교가
항상 거짓이 되어 전 케이스가 FAIL이 됩니다. 그래서 입력 경계에서 한 번만 `normalize_label()`을
통과시켜 내부에서는 **`Cross` / `X` 두 가지 표준 라벨만** 사용하고, 콘솔 출력과 PASS/FAIL 비교도
표준 라벨 기준으로 수행합니다. 해석할 수 없는 라벨(예: `"star"`)은 `None`을 반환해
해당 케이스만 FAIL로 남깁니다.

### 동점 처리 정책 (epsilon)

```python
if abs(score_a - score_b) < 1e-9:
    return UNDECIDED
return label_a if score_a > score_b else label_b
```

두 점수의 차이가 `1e-9` 미만이면 우열을 가리지 않고 `UNDECIDED`로 판정합니다.
판정이 `UNDECIDED`이면 `expected`와 같을 수 없으므로 FAIL로 집계합니다.

### 성능 측정

`measure_mac()`은 입력/출력/파일 읽기를 제외하고 `mac()` 호출 구간만
`time.perf_counter()`로 감싸 **10회 반복 측정 후 평균**을 ms로 반환합니다.

## 3. 결과 리포트

### 3-1. 실행 결과 요약 (`data.json`)

```
총 테스트: 6개
통과: 3개
실패: 3개

실패 케이스:
- size_5_1:  동점(UNDECIDED) 처리 규칙에 따라 FAIL (차이 1.110e-16 < 1e-09)
- size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (차이 2.665e-15 < 1e-09)
- size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL (차이 1.776e-15 < 1e-09)
```

| 케이스 | Cross 점수 | X 점수 | 차이 | 판정 | expected | 결과 |
| --- | --- | --- | --- | --- | --- | --- |
| size_5_1 | 0.9000000000000000 | 0.8999999999999999 | 1.11e-16 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | 8.8 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | 14.4 | X | X | PASS |
| size_13_2 | 7.4999999999999973 | 7.5 | 2.66e-15 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9000000000000004 | 4.8999999999999986 | 1.78e-15 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | 52.8 | Cross | Cross | PASS |

### 3-2. 실패 원인 분석

실패 케이스를 진단할 때는 원인을 **① 데이터/스키마 문제 ② 로직 문제 ③ 수치 비교 문제**로
나눠서 확인했습니다.

**① 데이터/스키마 문제인가?** — 아닙니다.
`filters`의 키(`size_5`/`size_13`/`size_25`)와 `patterns`의 키(`size_{N}_{idx}`)에서 뽑은 N이
모두 일치했고, 각 `input`의 행/열 수도 N과 일치했습니다. 다만 `expected`는 `'+'`/`'x'`,
필터 키는 `'cross'`/`'x'`로 표기가 달라 **라벨 정규화를 하지 않았다면 6건 전부 FAIL**이 됐을
문제가 있었습니다. 이건 정규화 계층을 두는 것으로 해결했습니다.
(고의로 크기가 다른 패턴, 없는 `size_7` 필터, `broken` 같은 잘못된 키, 해석 불가 라벨을 넣어 본
테스트에서도 프로그램이 중단되지 않고 해당 케이스만 사유와 함께 FAIL로 남는 것을 확인했습니다.)

**② 로직 문제인가?** — 아닙니다.
MAC 결과를 `fractions.Fraction`으로 오차 없이 다시 계산해 검증했더니, 실패한 3건은
**수학적으로 두 점수가 정확히 같은 값**이었습니다. size_5_1은 Cross = X = 9/10,
size_13_2는 Cross = X = 15/2, size_25_1은 Cross = X = 49/10입니다. 즉 이 데이터들은
"어느 한쪽으로 판정할 수 없게" 의도적으로 만들어진 케이스이고, 곱셈/누적 로직은 정상입니다.

**③ 수치 비교 문제인가?** — 예, 여기가 핵심입니다.
`data.json`의 필터에는 `0.1`, `0.3` 같은 값이 들어 있는데 이 값들은 이진 부동소수점으로
정확히 표현되지 않습니다. 그래서 더하는 **순서**만 달라져도 결과가 미세하게 갈립니다.
실제로 `0.3 + 0.3 + 0.3 = 0.8999999999999999`인 반면 `0.9`는 `0.9000000000000000222`로,
같은 9/10인데도 1.11e-16만큼 차이가 납니다. 이 오차는 크기가 커질수록 누적되어
25x25에서는 1.78e-15까지 벌어졌습니다.

만약 `if score_cross > score_x:` 처럼 **단순 비교**를 썼다면 프로그램은 이 1e-16짜리
쓰레기 값을 근거로 size_5_1을 "Cross"라고 **자신 있게 틀리게** 판정했을 것입니다
(정답은 X). size_13_2와 size_25_1도 마찬가지로 잘못된 라벨이 나옵니다. 결과적으로
FAIL 개수는 3개로 똑같지만, 의미는 완전히 다릅니다. epsilon 정책은 "틀린 확답"을
**"판정 불가라는 정직한 답"**으로 바꿔 줍니다. 그래서 이번 3건의 FAIL은 고쳐야 할 버그가
아니라, 동점 데이터에 대해 규칙대로 동작한 **정상적인 실패**로 판단했습니다.

남은 선택지는 정책의 문제입니다. `1e-9`를 더 키우면(예: `1e-2`) 실제로 가까운 두 패턴까지
동점으로 뭉개고, 없애면 위처럼 오차가 판정을 지배합니다. 점수 규모가 커지는 경우까지
고려하면 절대 오차 대신 상대 오차(`abs(a-b) <= 1e-9 * max(abs(a), abs(b))`)로 확장하는 것이
다음 개선 방향이라고 생각합니다.

### 3-3. 성능 분석

```
크기         평균 시간(ms)        연산 횟수
------------------------------------------
3x3        0.0075           9
5x5        0.0180           25
13x13      0.0965           169
25x25      0.3416           625
```

(측정 환경: macOS / Python 3.9.6, MAC 연산 구간만 10회 반복 평균. 값은 실행할 때마다 조금씩 달라집니다.)

| 크기 | 연산 횟수(N²) | 3x3 대비 연산 횟수 | 3x3 대비 측정 시간 | 곱셈 1회당 시간 |
| --- | --- | --- | --- | --- |
| 3x3 | 9 | 1.0배 | 1.0배 | 0.83 µs |
| 5x5 | 25 | 2.8배 | 2.4배 | 0.72 µs |
| 13x13 | 169 | 18.8배 | 12.9배 | 0.57 µs |
| 25x25 | 625 | 69.4배 | 45.5배 | 0.55 µs |

`mac()`은 행 루프 N번 × 열 루프 N번, 즉 **N² 번의 곱셈-누적**을 수행하므로 시간 복잡도는
**O(N²)** 입니다. 측정값도 이를 뒷받침합니다. 연산 횟수가 69.4배로 늘 때 시간은 45.5배로
늘었고, **곱셈 1회당 시간이 0.83 µs → 0.55 µs로 비교적 일정한 범위**에 머뭅니다.
시간 배수가 연산 횟수 배수보다 다소 작게 나오는 이유는, 함수 호출·크기 검증·루프 준비 같은
**고정 비용이 작은 행렬에서 상대적으로 크게 잡히기 때문**입니다. 3x3은 곱셈이 9번뿐이라
고정 비용이 전체 시간의 큰 몫을 차지하고, 그만큼 기준값(1.0배)이 부풀려져 있습니다.
N이 커질수록 이 고정 비용의 비중이 줄어 곱셈 1회당 시간이 점점 낮아지며 실제 연산 비용에
수렴합니다.

여기서 확인해야 할 것은 "N이 2배가 되면 시간이 2배"가 아니라 **"N이 2배면 시간이 4배"**라는
점입니다. 실제로 13x13(0.0965 ms) 대비 25x25(0.3416 ms)는 N이 약 1.92배일 때 시간은 3.54배로,
1.92² = 3.70에 가깝습니다. 고정 비용의 영향이 작아지는 큰 크기끼리 비교했기 때문에 제곱 관계가
더 뚜렷하게 드러납니다. 이것이 O(N)이 아니라 O(N²)라는 직접적인 근거입니다.
이 추세를 그대로 늘리면 100x100은 약 5.5 ms, 1000x1000은 약 0.55초가 되고, 실제 AI 모델처럼
필터를 수천 개 쓰면 이미지 한 장에 수백 초가 걸립니다. CPU가 이 단순 반복을 순서대로 처리하는
대신, 수천 개의 MAC을 동시에 처리하는 NPU가 필요한 이유가 여기서 드러납니다.
